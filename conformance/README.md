# Conformance baseline

The golden legacy and v0 transfer messages in `test/test_solana.ml` use the
wire layouts implemented by Agave `v4.2.1`:

- `solana-message` `4.2.3`
- `solana-transaction` `4.1.4`
- `solana-short-vec` `3.2.2`
- `solana-system-interface` `3.2.0`

The vectors deliberately use repeated-byte public keys and blockhashes so every
field and boundary can be inspected directly. The expected bytes are literals,
not output generated by the OCaml encoder during the test. The v0 fixture loads
the writable destination from lookup-table index 1.

`@solana/kit` `8.0.0` is the client-side compatibility target. The checked-in
token vectors cover PDA/ATA derivation, idempotent ATA creation,
`TransferChecked`, and v0 lookup-table resolution. Kit and Agave deliberately
have separate legacy fixtures: both messages have the same intent, but their
compilers choose different valid account-key orders. OCaml compilation must
match Agave byte-for-byte and must decode and policy-check both outputs.

The `sdk-conformance` CI job runs on the organization-owned Linux/X64 builder
and regenerates both files from exact lockfiles:

```sh
npm ci --prefix conformance/kit
npm run generate --prefix conformance/kit
cargo run --locked --manifest-path conformance/agave/Cargo.toml
```

Ordinary OCaml tests consume only checked-in fixtures and never install packages
or query an RPC endpoint.

Message version 1 is intentionally absent from the positive fixture set and has
a negative fixture: it remains pending activation at this baseline and its wire
format is rejected explicitly.
